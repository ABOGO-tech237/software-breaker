Cloud Agents, sur nos projets.

Même agent qu’en local. Autre machine. Branche isolée. PR à relire.

15–20 min · français · slides + notes · faits vérifiés sur cursor.com/docs

Pourquoi ce talk

L’agent local suffit… jusqu’au plafond du laptop.

  • Plusieurs agents se marchent dessus et se partagent CPU, ports, fichiers.
  • Une tâche longue t’oblige à rester connecté.
  • Vérifier l’UI sans casser ton checkout courant est pénible.

Docs : cloud-agent.md — parallèle sans laptop en ligne. Blog Computer Use — conflits locaux.

Définition officielle

Mêmes fondamentaux d’agent, dans une VM isolée.

Le cloud clone le repo, installe l’environnement, et travaille comme un laptop de dev : deps, secrets, commandes de start, réseau.

  • Peut builder, tester, et interagir avec le logiciel modifié.
  • MCP autorisé (HTTP recommandé ; stdio dans la VM).
  • Multi-repos possible ; le mode long-running n’y est pas encore.

Cloud vs local

Ce n’est pas le même disque.

Agent local

  • Tourne sur ta machine, sur ton checkout.
  • Worktree git : checkout isolé, parallèle sur le laptop.
  • Checkpoints locaux, hors git.
  • Hooks / skills de ~/.cursor disponibles.

Cloud Agent

  • VM Ubuntu isolée, laptop optionnel.
  • Clone depuis GitHub / GitLab / Azure DevOps / Bitbucket.
  • « Move to Cloud » : historique de chat, pas les fichiers non commités.
  • Skills projet dans le repo ; skills perso si Sync Skills.

Comment ça travaille

VM isolée → branche à part → PR draft.

  • Start depuis web, IDE, CLI, Slack, issue/PR, API.
  • Provision : microVM Firecracker, clone autorisé uniquement.
  • Run sur une branche séparée (pas ton worktree local).
  • Handoff : push + PR draft ; commits signés HSM Ed25519 (Verified).
  • Un agent ne voit pas le code ni l’état d’un autre agent.

Computer Use

L’agent a un bureau. Tu peux le prendre.

  • Souris + clavier + navigateur dans la VM (comme un humain).
  • Dev server → parcours UI → vérif avant la PR.
  • Artefacts : captures, vidéos, logs — optionnellement dans la description GitHub.
  • Remote desktop control : tu testes sans checkout local, puis tu rends la main.

« Try Live » : non trouvé dans les docs officielles. capabilities.md · blog/agent-computer-use

Bons usages documentés

Déléguer ce qui se vérifie tout seul.

  • Feature, bug, tests, PR pendant que tu n’es pas devant la machine.
  • Plusieurs agents en parallèle, sans saturer le laptop.
  • Tâche qui traverse frontend / backend / infra (environnement multi-repos).
  • Kickoff depuis Slack, GitHub, Linear — puis suivi CI / commentaires (subscriptions).
  • Auto-fix CI GitHub Actions sur les PR créées par l’agent (plan Teams).

Limites documentées

Ce que le cloud ne fait pas (encore).

  • Sans environnement préparé, l’agent écrit du code qu’il ne peut pas prouver.
  • Pas tes edits locales non commitées. Pas tes hooks ~/.cursor.
  • Long-running indisponible en multi-repos. Auto-CI : Teams + GHA seulement.
  • Pièces jointes web : 4 Mo docs / 15 Mo vidéo. ZIP non supporté.
  • Risque d’injection de prompt + exfiltration : restreindre l’egress.
  • Cette VM ne voyait pas les chemins frères du laptop.

À emporter

Local pour itérer. Cloud pour isoler et prouver.

  • Le cloud n’est pas « plus magique » : c’est un laptop jetable + git.
  • La qualité suit l’environnement (install, secrets, réseau).
  • La revue humaine reste le merge gate — PR draft, commits signés.
  • Sur nos repos privés : d’abord les connecter, ensuite déléguer.
